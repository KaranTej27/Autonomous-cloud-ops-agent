# Code of conduct

## Our commitment

We want this project to be a good place to learn about cloud reliability, defensive security, and AI systems, at any experience level. Everyone who takes part agrees to follow this code of conduct. That includes maintainers, contributors, reviewers, and people who report issues.

## Expected behaviour

- Be respectful and patient, especially with people who are new to the project or to the field.
- Give feedback on the work, not the person.
- Assume good intent. Ask questions before you conclude someone is wrong.
- Expect reviewers to ask for changes, and explain your reasoning when you disagree.
- Credit other people's work and ideas.

## Unacceptable behaviour

- Harassment, insults, or discriminatory language and jokes.
- Personal attacks, or repeated disruption of discussions.
- Sexualized language or imagery.
- Publishing someone's private information without their permission.
- Threats of any kind.

## Project-specific expectations

This is a defensive security project, so a few extra rules apply:

- Do not share credentials, private logs, or real personal data in issues, pull requests, or discussions.
- Do not post exploit code or attack instructions aimed at real systems. Simulated lab scenarios belong in [scenarios/](scenarios/) and must be labelled as simulated.
- Do not test this project, or any technique discussed here, against systems you are not authorized to test.
- Report vulnerabilities privately, as [SECURITY.md](SECURITY.md) describes, not in public threads.

## Scope

This code applies in every project space: the repository, issues, pull requests, discussions, and any chat or meeting the project runs. It also applies when someone represents the project in public.

## Reporting

If you experience or see unacceptable behaviour, report it to the maintainers:

> Contact: *to be added by the maintainers before the project accepts outside contributions.*

Maintainers will review every report and keep the reporter's identity confidential. If a report involves a maintainer, that maintainer takes no part in handling it.

## Enforcement

Maintainers choose a response based on the impact of the behaviour:

1. Correction. A private message that explains what was wrong and what is expected.
2. Warning. A formal warning that states the consequences of continued behaviour.
3. Temporary ban. A time-limited ban from interacting with the project.
4. Permanent ban. Removal from all project spaces.
